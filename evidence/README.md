# Recorded verification

These files are outputs from actual local software execution. Hardware and workload measurements stay synthetic. They are a reproducibility record, not proof of production-scale performance or real GPU qualification.

| Evidence | What it establishes | Limit |
|---|---|---|
| [test-verification.json](test-verification.json) | 85 passing lifecycle, API authorization, concurrency, crash, alert-audit and OTLP delivery contracts | Local software tests; the physical burn-in skip is a qualification record, not a skipped unit test |
| [stack-verification.json](stack-verification.json) | 17 recorded readiness/integration checks; real backend retrieval; real Temporal worker stop/restart, 57 history events and one ticket | Single-host native macOS arm64 development stack; simulated technician/hardware/workload |
| [telemetry-contract.json](telemetry-contract.json) | Actual Mimir metric-label names and Loki indexed series; incident/trace/request IDs do not multiply the metric or Loki index labels | Small local dataset, not a cardinality load benchmark |
| [binary-manifest.json](binary-manifest.json) | Pinned official release versions and verified published archive/binary SHA-256 digests | Checksum verification, not a source-code or supply-chain audit |
| [grafana-live.jpg](grafana-live.jpg) | Actual Grafana view reading the running Mimir-backed signals | Synthetic hardware; a capture at one point in the run |
| [walkthrough-hero.jpg](walkthrough-hero.jpg), [walkthrough-mobile.jpg](walkthrough-mobile.jpg) | Actual desktop and 390px mobile website captures | Artwork is conceptual; animation explains the recorded operation |

Reproduce the software tests with `python3 -m unittest discover -s tests -v`. Reproduce the native integration with the [README](../README.md) commands and `scripts/verify_stack.py`; use a fresh runtime database. `web/evidence.json` contains 50 frames across six scenarios generated by `scripts/record_replays.py`, with a deterministic lab clock and generated fictional IDs. It records state, history and provenance rather than hand-authoring successful outcomes.

The delivery probe deliberately sends to an unreachable loopback port, observes pending durable records, and replays them through the actual Collector. That proves the **application outbox retry** boundary. It does not claim that a Collector process or backend disk was fault-injected. Unit tests separately cover rejected and partially accepted OTLP delivery.

The local probes measure 20 CPU digest operations and cache-inclusive temporary-file round trips with checksum verification. Their timings describe that laptop run. There is no `fsync`, cache eviction, GPU, RDMA, power or distributed benchmark in those numbers.

The native startup checks reject occupied ports. Service discovery explicitly advertises loopback; Mimir gossip also binds loopback on 37946. Backend data-plane tenant isolation is disabled for this internal local profile; tenant authorization is demonstrated in the control API.
